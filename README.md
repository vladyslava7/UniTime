# UniTime (Де Пара?)

## Проблема
Студентам важко орієнтуватися в університетському розкладі через постійні зміни: чергування чисельника/знаменника (парних/непарних тижнів), раптові перенесення лекцій в інші аудиторії чи на платформи (Zoom/Google Meet), а також через необхідність щодня шукати потрібні посилання на онлайн-зустрічі у безлічі чатів месенджерів.

## Рішення
Застосунок є розумним розкладом, який автоматично адаптується під поточний тиждень (чисельник чи знаменник). Він дозволяє в один клік закріпити за кожним предметом посилання на онлайн-лекцію, ID конференції або номер аудиторії. Напередодні пари застосунок надсилає push-сповіщення з готовим прямим лінком для швидкого входу на заняття.

## Цільовий користувач
Студенти та старости академічних груп, які хочуть мати актуальний розклад із усіма необхідними посиланнями в одному зручному місці та уникати запізнень на заняття.

---

### 1. User Stories
* **Як студент**, я хочу отримувати термінове push-сповіщення, якщо посилання на лекцію або статус пари змінюється менш ніж за 30 хвилин до її початку, щоб не чекати викладача в порожній онлайн-кімнаті.
* **Як староста**, під час оновлення посилання на онлайн-лекцію я хочу, щоб система автоматично перевіряла базу даних і попереджала мене, якщо цей самий лінк (наприклад, кімната Zoom) вже закріплений за іншою групою на цей же час, щоб уникнути накладок.
* **Як студент**, я хочу бачити в особистому кабінеті зведену статистику (відсоток скасованих пар, співвідношення лекцій та практик), щоб аналізувати своє академічне навантаження.
* **Як користувач**, я хочу мати можливість згенерувати унікальне `.ics` посилання, щоб мій розклад автоматично синхронізувався з моїм Google Calendar або Apple Calendar.

### 2. Вимірювані обмеження (Non-Functional Requirements)
* **Performance (Продуктивність):** Час відповіді сервера (Response Time) на запит отримання розкладу на день (`GET /api/v1/schedule/today`) не повинен перевищувати 300 мс при 95-му перцентилі навантаження.
* **Availability (Доступність):** Система повинна гарантувати аптайм (Uptime) на рівні 99.9% у робочі години університету (з 08:00 до 18:00), щоб студенти завжди мали доступ до посилань перед парою.
* **Security (Безпека):** Усі маршрути для зміни даних (створення, редагування посилань) повинні бути захищені. Тільки користувачі з підтвердженим JWT-токеном та роллю `STAROSTA` або `ADMIN` мають право на виконання `PUT`/`POST` запитів.

### 3. Дизайн ключових ендпоінтів (Request/Response контракти)

#### Ендпоінт 1: Отримання розкладу з підтримкою статусів скасування
**`GET /api/v1/schedule/today`**

* **Request:**
  * Headers: `Authorization: Bearer <JWT_TOKEN>`

* **Response (200 OK):**
```json
{
  "date": "2026-05-25",
  "week_type": "numerator",
  "classes": [
    {
      "class_number": 1,
      "time": "08:00 - 09:20",
      "subject": "Диференціальні рівняння",
      "status": "active",
      "join_url": "[https://zoom.us/j/123456789](https://zoom.us/j/123456789)"
    },
    {
      "class_number": 2,
      "time": "09:35 - 10:55",
      "subject": "Теорія ймовірностей",
      "status": "cancelled",
      "cancellation_reason": "Викладач на лікарняному",
      "join_url": null
    }
  ]
}
```

#### Ендпоінт 2: Оновлення посилання на пару із захистом від конфліктів
**`PUT /api/v1/schedule/classes/{class_id}/link`**

* **Request:**
  * Headers: `Authorization: Bearer <JWT_TOKEN>`
  * Body:
```json
{
  "new_url": "[https://zoom.us/j/987654321](https://zoom.us/j/987654321)",
  "platform": "Zoom"
}
```

* **Response (409 Conflict):** *(Спрацьовує логіка захисту від накладок)*
```json
{
  "error": "ConflictDetected",
  "message": "Ця кімната Zoom вже використовується іншою групою на цей самий час."
}
```

* **Response (200 OK):** *(Успішне оновлення)*
```json
{
  "status": "success",
  "message": "Посилання успішно оновлено. Push-сповіщення надіслано студентам."
}
```

#### Ендпоінт 3: Отримання аналітики (Дашборд студента)
**`GET /api/v1/users/me/stats`**

* **Request:**
  * Headers: `Authorization: Bearer <JWT_TOKEN>`

* **Response (200 OK):**
```json
{
  "period": "current_month",
  "total_classes": 45,
  "cancelled_percentage": "15%",
  "lectures_to_practicals_ratio": "1:2"
}
```

#### Ендпоінт 4: Експорт розкладу (iCal Sync)
**`GET /api/v1/sync/calendar`**

* **Request:**
  * Headers: `Authorization: Bearer <JWT_TOKEN>`

* **Response (200 OK):**
  * Content-Type: `text/calendar`
  * Body: *(Повертає згенерований файл `schedule.ics` для автоматичної інтеграції з Google Calendar або Apple Calendar)*

### 4. Тест-кейси

**Тест-кейс 1: Захист від конфлікту ресурсів (накладок)**
* **Трасованість:** US-2 — Conflict Detection. API flow: обробка PUT-запиту на оновлення лінку.
* **Рівень тесту:** API / Integration
* **Пріоритет:** High

**Кроки (When):**
1. Авторизуватися в системі під роллю старости (отримати валідний JWT).
2. Відправити PUT-запит на `/api/v1/schedule/classes/{id}/link` з посиланням (наприклад, `https://zoom.us/j/111222333`), яке вже закріплене за іншою групою на цей самий часовий слот.

**Очікуваний результат (Then):**
* Система перевіряє базу даних на наявність дублікатів посилань в один і той же час перед збереженням.
* **PASS:** Запит відхилено. Повертається статус помилки `409 Conflict` із повідомленням про накладку. Зміни в БД не вносяться.
* **FAIL:** Запит успішно виконано (статус `200 OK`), посилання перезаписано, незважаючи на конфлікт.

---

**Тест-кейс 2: Синхронізація розкладу (iCal)**
* **Трасованість:** US-4 — Calendar Sync. UX flow: експорт розкладу у форматі .ics.
* **Рівень тесту:** Manual Smoke / E2E
* **Пріоритет:** Medium

**Кроки (When):**
1. Відкрити інтерфейс застосунку та авторизуватися як студент.
2. Натиснути кнопку "Експорт в календар" (ініціювати GET-запит на `/api/v1/sync/calendar`).

**Очікуваний результат (Then):**
* Система генерує файл розкладу, сумісний з Google/Apple Calendar.
* **PASS:** Файл формату `.ics` успішно завантажується, містить актуальні пари з правильними часовими мітками та посиланнями.
* **FAIL:** Файл не завантажується, завантажується з помилкою формату, або містить застарілі/порожні дані.

---

**Тест-кейс 3: Перевірка безпеки (Рольова модель)**
* **Трасованість:** US-Security — Role-based Access Control. API flow: перевірка прав доступу.
* **Рівень тесту:** API / Security
* **Пріоритет:** High

**Кроки (When):**
1. Авторизуватися в системі як звичайний студент (роль `STUDENT`, без прав старости).
2. Спробувати відправити PUT-запит на зміну посилання на будь-яку пару через ендпоінт `/api/v1/schedule/classes/{id}/link`.

**Очікуваний результат (Then):**
* Система перевіряє роль користувача в JWT токені перед виконанням дії, що змінює дані.
* **PASS:** Дія миттєво блокується, повертається статус `403 Forbidden`. Оригінальне посилання в базі залишається без змін.
* **FAIL:** Запит виконується (статус `200 OK`) або система повертає некоректну помилку без блокування дії на рівні бази даних.

# UniTime API

API для управління розкладом та посиланнями.

## Стек технологій
* Java 17, Spring Boot 3.2.5
* Maven
* Docker (Multi-stage build)
* Swagger UI (OpenAPI 3)

## Як запустити локально
1. Скопіюйте репозиторій: `git clone https://github.com/vladyslava7/UniTime.git`
2. Перейдіть у папку `api`: `cd api`
3. Запустіть проєкт: `./mvnw spring-boot:run`
4. Відкрийте в браузері: `http://localhost:8080/swagger-ui/index.html`

## Як запустити через Docker
1. Зберіть образ: `docker build -t unitime-api .`
2. Запустіть контейнер: `docker run -p 8080:8080 unitime-api`

## Посилання на деплой
Ви можете протестувати API в реальному часі за посиланням:
[UniTime Swagger UI](https://unitime-8df4.onrender.com/swagger-ui/index.html)
